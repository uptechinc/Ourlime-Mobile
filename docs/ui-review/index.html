Ourlime UI Review

Bug fixes from tester reports, a cleanup of crowded filter screens, a page-by-page polish pass and a production performance audit of the Android app and the website.

Mobile app

E-Projects: three rows of chips become one Filters button

Status, role and sort each had a full chip row, plus an Asc/Desc toggle. They now sit in a bottom sheet, with a count on the button and a removable chip for each active filter. Sort and direction merged into plain choices such as Name A–Z. The empty band above the header is also gone: the page was adding the status-bar inset twice.

Task details: typing stays visible above the keyboard

Raushawn could not see what he typed. On Android the keyboard covered the comment and log-time fields inside the sheet. The sheet now lifts above the keyboard.

Project settings: delete button stays inside the sheet

Delete Entire Project spilled out below the sheet. The sheet now scrolls and keeps every control inside it.

Project activity reads as plain English

Recent Activity showed internal keys like add_subtask and time, twice per entry. It now reads “added a subtask”, “commented”, “logged time”.

Community posts: comment and share counts survive a refresh

Chris reported counts disappearing. The app saved community comment and share counts in the wrong place and read them from a field nothing writes, and the card kept whatever number it first loaded. Counts now come from the same counter the website uses, comments are counted directly, and the card follows the refreshed number. This post has one comment and one share.

Hosting an event: crop the cover, add a poll

Picking a cover only showed a file name, with no preview and no way to crop. The photo now opens the crop screen, then shows as a preview with Crop, Replace and Remove. Chris’s suggestion is in too: a Yes/No Add a poll? toggle that creates a community poll closing when the event starts.

Blogs: one row of categories

The page stacked a type toggle, categories and a long tag row before any content. Categories stay on the page; type, sort and tags (pick several) moved into the existing filter button, which now shows a count.

Admin: Users and Reports

Two labelled chip rows on each screen became one Filters button. Labels such as under_review now read “Under review”.

Website at phone width

Desktop and tablet layouts are unchanged. Below 640px the same controls move into a bottom sheet behind one Filters button.

E-Projects

Three full-width dropdowns and a direction button took five rows before the first project.

Blogs

Type, sort and all popular tags sat above the posts, and the page said No blogs found while it was still loading. It now says “Loading blogs…”, and a blank tag pill is gone.

Admin pages

Users had four wrapping dropdown buttons. Reports had three labelled dropdowns, and its tab row broke words mid-way (“Repo / rts”). Activity Logs had two fixed-width dropdowns over three rows.

Who can see what

Each page’s availability is set by admins in Page Access. Restricted pages were only half enforced: the app’s tab bar ignored the settings, and both the app and the website drew restricted pages behind a see-through overlay while linking to them from every menu. Now a page someone can’t open is neither listed nor rendered for them. The screenshots below were taken with this admin account temporarily treated as a regular user.

App: tabs and menu only list what the account can open

The Limes tab matched no setting because tab paths are capitalised (/Limes), so admin-only Limes stayed open to everyone. The same mismatch hid the website’s /messages and /profile/settings settings from the app. Restricted tabs and menu items are now removed, the blocking screen is fully opaque, and Limes videos never play behind it.

Website: restricted pages are never rendered or linked

The overlay was 50% black with blur, so the restricted page still rendered and loaded its data underneath, and greyed-out links stayed in the top bar, feed tabs, profile menu, bottom bar and Games card (which offered admin-only Trini Wordle). Restricted pages are now withheld until access is confirmed, every nav hides them, and the last known settings are cached so this check doesn’t slow the first paint.

Communities

Comment counts agree everywhere, and posts load faster

The website increased one field when someone commented and displayed a different one, while the app wrote a third. Both now count the comments themselves, so the app, the website and the database agree. The website’s community posts were built with about five database reads per post; they now use a handful of batched reads, and a second call that re-read every post and every like counter in all communities was cut down to this community only. Moderated (hidden) community posts were also still shown on the website because the hidden flag was dropped; they are now filtered.

  • App directory: the Communities list made six database round trips one after another. Independent ones now run together (13.5 s → 10.8 s on the emulator), and the list is now warmed in the background at startup like the feed, so it opens filled.
  • Website community page: posts arrive in about 3 s on the local development server after the first compile.

Fixes without a screen

  • Chat archive. Unarchiving from inside a chat now takes it out of Archived, and it stays out after a restart. The list used to rebuild from a stale local copy.
  • Manage Jobs crash. The screen crashed on open because the app’s runtime lacks Promise.finally. All 16 uses across the app were replaced.
  • Status bar. After visiting Limes, the clock and battery icons turned white on light screens such as Communities. Limes now sets its dark status bar only while it is open.
  • Event poll toggle. The selected Yes/No option no longer stays faded after tapping.
  • Members count. The project stat now counts accepted members only, matching Team Members.
  • Roles and permissions guide. A rule file for AI agents in both repos explains that “Administrator Access Required” pages, such as a shared Lime, are an admin choice and not a bug.

Polish pass

A page-by-page sweep of both apps for small, high-impact fixes: honest loading states, readable labels, theme colors, touch targets and spacing. Layouts, navigation and page structure were left alone; anything bigger is listed under Recommendations.

Events and Market say “Loading” instead of “0”

While data was on its way, Events read 0 upcoming community and public events, and Market and E-Hub read 0 listings loaded. Both looked like empty pages. They now say they are loading until the data arrives. Jobs got the same treatment on both platforms.

Settings: account fields stay together

The policy links sat between First Name and Last Name. They now follow the account fields, in the same tab.

Courses and cart read cleanly

The course catalog showed Programming three times because the category list has duplicate names. The saved cart opened with a fragment, “synced. Items do not reserve stock.” Each status is now a full sentence.

Website: greeting, sign-in hints and status chips

E-Learning greeted people by email address and showed Don&apos;t in a course message. Help showed Sign in required on every card to people already signed in. E-Projects chips showed raw values such as active and owner.

Recommendations

Larger changes the audit points to. None of these is implemented: each needs your call because it changes security behavior, data shape, indexes or page structure.

Speed

  • Rate limiting serializes parallel API calls (website). Every API request runs a Firestore transaction on one per-user, per-minute document, so a page’s parallel requests queue behind each other, and 5–51 middleware checks per run hit the 3.5 s timeout. Options: rate-limit only writes, or count with atomic increments and no transaction. This is a security trade-off, so it’s yours to decide.
  • Middleware checks access over HTTP (website). Each page and API request makes a second HTTP request to /api/security/check-access. Doing the check inside the middleware with a short cache would remove that hop.
  • Notifications read 150 to show 20 (website). The “unread first” sort loads up to 150 items per request. Querying unread items separately needs a composite index on isRead + createdAt, which means deploying an index.
  • Blogs load interactions one blog at a time (website). Returning the viewer’s likes and bookmarks with the blog list would remove six requests per page. This changes the API response shape.
  • One slow connection carries every read (app). Forced long-polling sends all Firestore traffic through one channel, so background refreshes delay the screen in front of you by 4–18 s (Jobs took about 20 s to show). Options: try auto-detected long-polling on real phones, or move to the native Firestore SDK, which is a larger migration.
  • Opening a link re-runs feeds (app). One Blogs open from a link ran the home feed and communities feed five times each (401 reads). The trigger needs tracing.
  • Remaining N+1 reads (app). Discover suggestions (152 reads), job questions (13 per screen), blog engagement (14), product images (11) and event attendees (6) can each be batched with in queries. This is straightforward follow-up work.
  • Comment totals counted post by post (app). 30 count queries per community feed refresh. A server-maintained counter would remove them; that needs a Cloud Function.
  • Same documents re-read at startup (app). Your user document is read 15 times and account settings 10 times. A shared profile cache would fix it.
  • Profile loads relationships twice (website). The relationship status and follower counts are each requested twice, and Home loads drafts twice with different filters.

Design and structure

  • Headers differ across pages: games, help, tickets and policies use the Advertise header.
  • Community detail has four differently saturated action buttons. They need one primary action and quieter secondaries.
  • On phones, the admin “Preview” pill overlaps the open-in-app banner.
  • Child Safety and Support admin pages still use solid blue buttons and links, which the admin color rule reserves for neutral styling. Restyling those primary actions goes past token fixes.
  • Events shows placeholder stats (“12,500 Happy Users”, “4.3 Rating”, “98% Energy Level”) next to the real count. Remove them or replace them with real metrics.
  • The app’s notifications list, Discover sections and Limes viewer show “nothing here” when a load fails. Error states there need new state plumbing.
  • The home feed stretches with the screen at extra-wide sizes; capping it changes its three-column grid.

Correctness found along the way

  • The website market API returns 0 products while admin shows approved listings.
  • /verify/[uId] writes users.verified from the browser.
  • Some routes the code calls don’t exist: /api/wallet/balance, /api/wallet/transfer, /api/ads/proof/pending, /api/user/profile.
  • Help staff pages are public at the middleware level. The pages still check roles.
  • In the app, the event link target and the job apply parameters are ignored, /jobs/[id] is unreachable, and the privacy and terms screens have no entry point.

Still open

  • Blogs with no author. Traced in the database: “Rishi’s Lily Farm” belongs to Rishi Kowlessar (viewed and liked 24 seconds after it was posted, name in the title) and “The Future of E-Project” to Chris Walker (opened on the website 34 seconds after it was posted from the app). “The End of the Chatbot Era” copy is a word-for-word duplicate of Krishna’s post, and “Test 3” is filler. The fix (assign two, delete two with a backup) is ready but changes live data, so it is waiting for approval.
  • Limes page description in Page Access reads “Social posts and conversations”. An admin can change it there.
  • Firestore connection on the app. Every read uses forced long-polling, which costs seconds per round trip on slow networks. Automatic detection was slower in testing, so it stays for now.
